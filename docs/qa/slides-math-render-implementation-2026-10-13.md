# Slides native math rendering implementation — 2026-10-13

## Behavior

Slides now draws OMML-derived MathML inside its shared Konva shape renderer. `pptx-render` treats each native equation as one atomic text-layout run, including during bidirectional layout, carries its source paragraph/run identity, and reserves width and extra line height for fractions, roots, scripts, large operators, matrices, and imported multiline equation arrays. Width follows the rendered MathML structure: stacked fractions take their widest branch, adjacent terms add horizontally, scripts and roots reserve their adornments, and matrix columns take their widest cells. It no longer reserves the often much longer linear fallback string, which caused visible gaps around mixed equations in the first GUI/PDF acceptance image. The line-height estimate follows the tallest nested branch, so parallel fractions do not compound height; matrix and equation-array rows accumulate vertically. Ordinary runs before and after the equation retain their own positions and styles. The authoritative `TextRun.rawXml` is never rewritten for display.

The renderer measures the MathML in Chromium, places it in a transparent, self-contained SVG data-URI image, and draws that image in `NodeBody` in place of the equation's linear fallback. It uses the run's font size and color. Shape rotation, group transforms, flips, text-body vertical rotation, foreground overlap, and table-cell order pass through the same Konva tree as other slide objects. The former top-level HTML overlay has been removed; its rectangular covering and fixed horizontal orientation no longer determine the result. Equation selection/editing remains tied to the native shape; a canvas double-click can reopen a selected equation without depending on an overlay DOM node.

Image and PDF export both call `renderSlidesToPngBase64`, which now waits for all equation images in shapes, groups, and table cells before calling Konva `stage.toDataURL`. Rasterization failure rejects export instead of producing a success status with missing math. PDF keeps the application's existing raster-page design; math is visible in the page image rather than searchable/vector PDF content. The SVG contains no external resource references. Chromium's SVG `foreignObject` in data-URI images was independently checked in a real Electron probe by the coordinating agent; final rebuilt-app PNG/PDF visual acceptance also passed, as recorded below.

## Accepted visual verification and remaining limits

- MathML dimensions are measured by Chromium for the image, while main-process text layout reserves a deterministic structural estimate. Complex imported equations can therefore still have some extra spacing or be scaled down within their reserved inline slot. The raw OMML remains intact, and adjacent ordinary text is not overwritten. The rebuilt visual comparison passed: mixed-text spacing is compact in the final PNG and Poppler-rendered PDF.
- Run shadows and the existing flip/scale/rotation transforms are carried to the image; uncommon gradient/outline/WordArt equation styling may differ from native PowerPoint rendering. The math font also depends on the local Chromium/Cambria Math fallback.
- The coordinating agent ran the rebuilt Electron editor and actual GUI PNG/PDF exports. The case passed in 5.3 seconds with two full-process reopens and an intervening equation edit. Root and Luna inspected the final PNG/PDF page and saved native PPTX. The E2E now uses canvas/model coordinates after overlay removal.
